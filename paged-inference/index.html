Building a paged inference engine from scratch, and measuring it honestly

A mini LLM inference server implementing the core ideas behind vLLM: a block-based paged KV cache, a continuous batching scheduler, and a FlashAttention-2 kernel rewritten to read and write through a block table, built without referencing vLLM's source. Every benchmark here ran against a naive sequential baseline, and at the model scale and sequence lengths I tested, the naive version wins on raw throughput. That result, and why, is most of this writeup.

Vraj Patel · August 2026 · github.com/VrajPatel105/paged-inference-engine
01  What this is

This is a self-directed, roughly 3-week build of a mini LLM inference server, implementing the core mechanisms behind vLLM: a block-based KV cache allocator, a continuous batching scheduler, a FlashAttention-2 kernel rewritten to read and write through a block table instead of contiguous per-sequence buffers, and INT8 KV cache quantization on top of all of it. I didn't look at vLLM's source while building this. Working out the mechanisms myself is where the actual understanding is, and it's the only way I'd know for certain what my version does and doesn't handle.

The rule for the benchmarks was the same one I used on my last GPU project: compare against something real, not against a worse version of yourself. Here that meant a naive baseline: no KV cache reuse, no batching, one request processed fully at a time, representing what you get with zero serving infrastructure. The honest result is that at the scale I tested, the naive baseline wins on throughput. I'm reporting that number and explaining why it happens, rather than picking a workload that flatters the paged engine.

02  Block allocator and continuous batching scheduler

The first piece is BlockManager (core/block_manager.py): a fixed-size pool of KV cache blocks with allocate, release_blocks, num_free_blocks, and can_allocate. Every sequence's KV cache lives across some number of these blocks instead of one contiguous buffer, which is the actual mechanism paging is named after. I tested it with interleaved-sequence correctness tests: allocate and free sequences in overlapping, out-of-order patterns and check that the free-block count and block ownership stay consistent throughout, not just at the end.

On top of that sits the scheduler (core/scheduler.py, core/sequence.py). Sequence tracks seq_id, prompt_token_ids, token_ids, and is_finished. Scheduler.schedule() runs four phases every call: _free_finished releases blocks for sequences that finished last step, _allocate_decode grows the block allocation for sequences still generating, _admit_waiting decides which queued requests get to start, and _build_output assembles the batch for this step. Whether a sequence is doing prefill or decode isn't stored as a flag anywhere. It's derived on the fly by comparing token counts, which keeps the state machine smaller at the cost of recomputing that comparison every call.

Admission has two modes. A skip-threshold mode blocks all new admissions until enough blocks are free, simple but can leave the GPU underutilized while waiting on one large request's blocks. A normal mode uses a lookahead window: if the sequence at the front of the queue doesn't fit right now, the scheduler can look past it and admit a smaller one instead, packing multiple admissions into a single call rather than stalling on the head of the line.

03  FlashAttention-2 kernel rewrite for pagingRTX 5080 Laptop

I had a standalone FA-2 kernel in Triton from an earlier project, the same one benchmarked in my prior GPU-inference writeup. Paging meant it could no longer assume each sequence's K/V lived in one contiguous buffer, so I rewrote the block-reading logic: new kernel parameters block_table, num_blocks_per_seq, q_len_per_seq, kv_len_per_seq, and block_size, with the inner loop now walking a sequence's block table to find where its K/V actually live in the pool instead of indexing a contiguous range.

Scrambling the block assignment mattered. A kernel that only gets tested on blocks laid out in allocation order tells you whether contiguous memory access works, which was never in question. It doesn't tell you whether the block-table indexing itself is correct.

04  Transformer surgery and the engine loop

The model is a decoder-only transformer, stripped down from an encoder-decoder transformer I built for an earlier project (cpp-gpu-inference/en-de-transformer): encoder and cross-attention removed. MultiHeadAttention.forward now writes new K/V into per-layer k_cache/v_cache buffers, registered with register_buffer at shape [num_blocks, num_heads, block_size, d_k], and calls the paged FA-2 kernel instead of the plain torch.cat-based KV cache from the earlier project.

The model runner (core/model_runner.py) is the loop tying everything together: drain the request queue, wrap each request in a Sequence, call scheduler.schedule(), and batch whatever it returns into one flat packed tensor for the step, prefill and decode sequences together, rather than a padded rectangular batch. One forward pass, then each sequence's last-token logits get pulled out with vectorized indexing, argmax'd, and the new tokens get written back.

A same-step bug worth mentioning

Sequences now stop and free their blocks as soon as they emit an EOS token, instead of always running to max_len. Implementing that surfaced an off-by-one: the batch index was only incremented inside the non-EOS branch, so a sequence hitting EOS mid-step would leave the index pointing at the wrong row for the rest of that step.

Fixed by incrementing the index unconditionally, outside the branch.

05  INT8 KV cache quantization

The last major piece. Granularity is per-block-per-head, symmetric quantization with no zero-point. The design I've been calling "B-approximate": the cache is int8 from the very first token, never staged in fp16 and quantized later. On every new token write, the block's existing filled entries get dequantized using the stored scale, the new token's real K/V gets appended, a new max-abs-based scale is recomputed over the whole set, and everything gets requantized back to int8 and written back along with the new scale.

On the read side, the Triton kernel loads the int8 tile and its per-block-per-head scale scalar, and dequantizes by casting and multiplying immediately before each of the two tl.dot calls: the QK^T and the post-softmax value aggregation.

Correctness validation

I ran the same 4 prompts through the live demo on two checkpoints: an FP16-only build from a commit before quantization existed, and the INT8 version. Both produced identical degenerate output, the model repeating "day day day the day the..." for all 4 prompts. That's the result I wanted. It means the quantization write and read path is mathematically correct and behaves identically to FP16, not that quantization broke something.

The repetition itself is unrelated to quantization. It's what you get from a small, lightly trained demo model under greedy argmax decoding, and fixing that wasn't in scope here, the point was serving infrastructure, not model quality. The identical-output test is exactly the kind of check that tells the two apart: if quantization had introduced a bug, the two checkpoints would most likely have diverged, not failed in the exact same way.

06  Benchmarking methodology

bench/benchmark.py is a standalone module. It doesn't import from train.py or model_runner.py, so a change to the serving code can't silently change what the benchmark measures.

The baseline is the original non-paged decoder-only transformer: plain scaled_dot_product_attention, no KV cache reuse, the full growing sequence reprocessed every decode step, one request run fully sequentially at a time. That's meant to represent the floor: what you get with no serving infrastructure at all.

TTFT (time to first token, prefill latency) and TPOT (time per output token, average decode step latency) are both measured with torch.cuda.synchronize() wrapping the timed region, to avoid timing CUDA's async dispatch instead of the actual work. I also measured aggregate throughput (total tokens generated / total wall time) across a concurrency sweep, and attempted a memory-ceiling test: the max concurrent sequences each approach could hold before OOM.

Warmup runs before timing starts mattered more than I expected. Without them, one-time CUDA and Triton kernel compilation gets counted as request latency. Paged TTFT measured ~1100ms before adding warmup, and ~69ms after, a compile-cost artifact, not anything close to the real per-request cost.

Naive stays flat, roughly 530-550 tok/s, regardless of concurrency. That's expected: it's fully sequential, so there's no batching interaction for concurrency to help with. Paged throughput climbs with concurrency but plateaus, and it never crosses naive's throughput anywhere in the tested range.

Honest interpretation. At this model size (small, from-scratch transformer) and these sequence lengths (roughly 50-95 tokens), the paged engine's fixed per-step overhead, Triton kernel launch, Python-side block table construction, query padding and unpadding, isn't amortized enough yet to beat a dead-simple sequential loop. That's a real and expected finding for infrastructure at small scale: paging and batching pay off once the workload is large enough that the problems they solve, no batching at all, memory fragmentation, requests blocking each other, actually start to hurt. Naive never gets stressed by this workload. It isn't memory-constrained, and nothing forces it to serialize in a way that costs it anything.

Why I'm not reporting a paged max-concurrency number as fact

The peak memory figure reported at the last successful point (n=64) was approximately 32 GB, on a 16 GB GPU. That isn't physically possible, so the number is wrong somewhere, not a real measurement of paged's memory ceiling.

Traced it to WSL2: CUDA allocations there can spill into a shared virtual memory pool backed by system RAM instead of failing cleanly at the real VRAM limit, which means torch.cuda.max_memory_allocated() isn't trustworthy for physical GPU capacity in this environment.

I could chase this down with an nvidia-smi-based measurement instead. I decided to report it honestly as inconclusive rather than publish a number I already know is wrong, given the throughput and TTFT/TPOT results above don't depend on it and stand on their own.

Two real bugs found along the way

  • num_blocks was set to 10000 (block_size=64, 6 decoder layers), which pre-allocates a large fixed KV cache pool, about 3.75 GB, at model construction time regardless of how many sequences are actually active. That's a real fixed cost of block-based paging worth knowing about, and it skewed early memory comparisons until I accounted for it.
  • Both models were staying resident on GPU at the same time during testing, naive and paged loaded together, which confounded early memory results. Fixed by explicitly freeing the naive model between test phases.
09  Scope explicitly not covered (v1)
  • No CPU offloading or recomputation-on-eviction. When memory runs out, the scheduler just blocks and waits for blocks to free up.
  • No speculative decoding, no beam search. Greedy argmax decoding only.
  • Model quality was never a goal here. The demo model is small and lightly trained on purpose. The repetitive output is expected and orthogonal to whether the serving infrastructure is correct.
10  Open items

Stated plainly, because a list of finished things with no unfinished things next to it isn't credible.

  • Re-measure the memory ceiling with an nvidia-smi-based check instead of torch.cuda.max_memory_allocated(), ideally outside WSL2, so max concurrent sequences is a number I can actually stand behind.
  • Test at a larger model and longer sequence lengths. The current results say paging's fixed per-step overhead isn't amortized yet at this scale. They don't say whether it ever crosses over, and that needs a bigger workload to answer.
  • Reduce the fixed per-step overhead itself, Triton kernel launch, Python-side block table construction, query padding and unpadding, since that's what's standing between paged and naive at every concurrency I tested.
  • CPU offloading, recomputation-on-eviction, speculative decoding, beam search. Not started.
